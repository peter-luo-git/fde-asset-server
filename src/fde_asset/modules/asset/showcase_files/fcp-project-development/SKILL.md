## 启动与流程技能

开始或恢复本技能覆盖的工作时，在继续任务分析、设计或实施前，先检查当前运行时提供的 Skill 清单，查找 Superpowers 的使用入口 `using-superpowers`。实际注册名可能带有命名空间，例如 `superpowers:using-superpowers`；结合清单中的名称、描述和来源确认入口，用技能工具加载实际注册的名称，不猜测工具或调用不存在的搜索接口。需要补查时，只在当前已授权的技能目录中按需读取入口。

读取入口后，遵循它的导航，根据当前任务加载适用的流程及专业 Skill，不预先读取整套正文，也不以本技能替代入口或重写一套固定任务分类。同一有效上下文中已读取且仍保有入口规则时继续遵循；上下文压缩、恢复后规则或版本不明时重新加载。相关技能的流程与本技能中的 FDE 需求来源、工作目录和交付规则共同适用，用户当前指令和平台权限边界保持优先。

入口或其要求的后续 Skill 不在当前可用清单、读取失败或资源不完整时，明确说明缺少哪个入口或技能，不假称已加载、已遵循或擅自安装。可独立完成的已授权工作继续进行；当前任务确实依赖缺失能力而无法继续时，再请用户补充关联或决定替代方式。技能加载本身不授予实施、推送、部署或额外工具权限。

## 需求讨论、设计与调整

已确认只修饰有真实用户来源的逐项需求，不修饰整份方案或版本号。引用旧版时保留每项的原归属；可以沿用上一版设计建议，但不能把其中仍待确认的技术选择一并称为“已确认的上一版”。局部确认只改变被回应的项目；开工仍允许合理默认，默认的来源不会因此改变。

先按上下文判断用户是在提出明确要求、询问可行性，还是回应某个问题，保留原话的确定程度。明确的新增或排除请求（如“加个重新开始”“悔棋先不要了”）可按其明确范围保存需求，不自行扩展实现细节。问号不是分类规则：“帮我加个按钮可以吗”在上下文中可能就是明确请求。

交付或修改设计、创建或更新任务、撰写 PR 说明时，完成以下发布流程：

1. 读取本轮明确来源及必要的真实讨论，结合题干与短答，把用户明确事项保存到当前工作记录；已有需求沿用同一 record 和当前版本。
2. 用 `fde_work_record_read` 读回当前记录，核对已保存的明确事项与仍未确定的范围，再按下述三类起草当前交付内容。
3. **发布前核对**整份公开答复、方案文档、任务描述、验收标准和 PR 说明：每个用户确认或范围排除的声明，都逐项对照原话或明确采纳的实际来源，包括引文同一句附加的限定及由此推导的基线。原话、作者身份与来源消息必须一起核对；多人会话的后续消息不默认来自最初请求者，以本轮明确来源或实际读取消息的 `author.id` 为准，`display_name` 仅用于展示。引用姓名须匹配同一消息的作者；无法核实作者时只引用原话和消息标识，不猜姓名，也不沿用上条发言者。单网页不等于用户确认无后端，两人轮流不等于用户确认同屏；原话旁新增的决定也需要独立依据。没有支持的内容移到建议／待确认，不因放在引用旁就归给用户。
4. **修正后复核**同一稿的前后归属，再发布已核对的版本；后文的“Agent解读／待确认”说明不能抵消前文已经作出的用户确认或排除声明。

公开答复、方案文档和需求摘要中的确认归属保持一致。交付设计时，将内容清楚区分为：

- **用户明确事项**：逐项附相关原话短引或实际已读来源，只涵盖用户实际表达或采纳的范围，短答结合被回应的题干。
- **Agent建议／实现选项**：合理推断、技术选择和设计默认放在这里，说明适用前提；例如用户只说“两人轮流”，可以建议同屏实现，但“同屏”仍是实现选项。
- **待确认问题**：保留原问题和未定范围，可给出建议，收到明确答复后再按其范围更新。

需求摘要只吸收用户明确事项，另外两类留在设计正文，需要归档时沿用下述讨论记录方式。方案可以采用合理默认继续展开，无需为每个技术选项追加持久问题、追问未来开工或重复审批；合理推断和既有确认字段不会把建议变成用户已决定的事项。

可行性、征询或含糊问句先自然回答并说明影响；例如“不判胜负会有什么影响？”在尚未明确采纳时仍是询问，不能直接改写成“用户已确认不做胜负”或“明确排除”。如需保留讨论，先读取当前工作记录及版本，用 `fde_work_record_write(kind=decision,state=recorded,expected_version=当前版本)` 保存原问题、相关来源和“讨论／待确认”，保持需求摘要不变。只有缺失答案会阻碍当前工作、且不能在已有授权范围内继续时才调用 `ask_user_question`，等待真实回答；普通方案交付不因未来是否开工而额外提问，已有明确许可不重复审批。

收到“对”“可以”“先不做”等短答时，结合本轮明确提供或按需实际读取的题干、答复及其指向逐项理解；明确确认的一项可更新，未回应的其他项仍保持原状态。先读同一 record 的当前版本，再用 `kind=summary` 和 `expected_version` 增补，局部修改用工具支持的精确 `edits`；关联实际已读题干和答复的 `source_message_ids`，不重建记录，也不默认注入全部历史。Agent建议单独标明，来源收据、版本号、`summary_confirmed` 或 `confirmed_version` 都不能替代用户实际表达的语义依据。

## 实施与交付

创建或更新任务时，把用户明确事项和 Agent 选定实现分别写入任务描述，验收标准也保留这一区分，沿用当前记录中的真实范围。写入前执行上述发布复核，写入后用 `fde_task_get` 读回实际任务，核对描述与验收的归属；发现混入建议时按当前版本修正并复核。开工许可允许在既有范围内采用合理默认，默认方案的来源仍是 Agent，不因此成为用户逐项明确要求。PR 说明沿用同一归属，不在转写、压缩或恢复中把建议提升为用户确认。

已确认的需求变化应同步到原任务，不能只更新聊天答复、设计文档或工作记录：先用 `fde_task_get` 读取当前描述、`acceptance_md` 与版本，再调用 `fde_task_update`，以当前 `expected_version` 更新受影响的描述和验收标准；读回核对后，在同一工作记录中保留变更前后内容及实际来源消息。任务已完成或关闭时，先按权限走原任务退回流程，再修改验收标准，不覆写已验收的标准快照。版本冲突时重新读取并合并当前需求，不覆盖他人的新标准。讨论建议、疑问和未采纳选项不写成用户确认的验收标准；局部确认只更新对应条目，不删除未改变的条件。标准改变后重新核对实现、验证与交付，不引用旧批准声称当前版本已通过。

任务退回（包括完成后退回）时，沿用原任务及历史记录，重新读取当前标准、状态、版本和关联 PR。历史 PR 的合并或批准不代表本轮交付通过：原 PR 已合并或关闭而本轮有代码修改时，推送本轮提交并新建明确关联原任务的 PR；原 PR 仍开启时，核对当前分支和精确 HEAD 后按授权更新。无代码变更的复验也须重新提供本轮验证与交付，不能套用旧 proof。按本轮标准重新检查、送审，等待新的评审与发起人验收；PR 合并、Agent 回复结束及历史验收都不能替代本轮验收。

先核对当前用户要求的交付范围。只设计就交付方案；明确实施通常查询并关联现有任务，没有才按需求、设计和验收标准创建一次，按任务工具及当前版本推进至进行中，再修改源码。用户明确不建任务时遵从。任务查询失败不能当作没有任务，也不能假称已登记；保留请求并幂等重试，期间可继续独立读取和设计。范围含糊、会改变当前执行动作且无法在已有授权范围内继续时调用 `ask_user_question`，等待真实回答；超时、跳过和无回复都不批准实施。

项目目录长期保留，任务/会话结束不清理源码。开始或恢复时核对当前项目根、涉及仓库、各仓实际 cwd、`git status`、当前分支、HEAD 和 `git worktree list --porcelain`。多个仓库独立管理历史、分支、提交和 PR，不能把同名分支当成匹配版本。缺目录、权限错误或路径未知时如实报告，不能把空目录说成旧成果不存在。

平台给每个会话或任务准备了专属工作目录：工作区根下 `sessions/<键>/`，本轮绑定里的 `project_workspace.session` 给出路径。私聊的工作区根是发起人的个人区（只有本人能看），频道会话和任务是项目共享区。专属目录是普通文件夹：文档、PPT、资料直接写在这里，人在页面上就能看和下载，不需要提交。要读写或提交代码时，先调用 `fde_workspace_open_repo(repository_id)` 在专属目录里打开对应仓库（本会话专属分支：任务 `task/<编号>`，会话 `chat/<编号>`），在返回的 `checkout_relative_path` 里改，不另建树、不切换它的分支；不要修改 `repos/` 下的仓库副本和 `sessions/` 下别的目录。本轮没有 `session`（老会话、老任务）时继续用原来的共享 checkout。用户没要求提交、推送或开 PR 时，成果留在专属目录，告诉用户文件路径即可（个人工作台「我的工作目录」能直接打开）。

新建前核对仓库、基线 SHA 和目标分支；通常使用已核实的远端默认分支，继续既有分支/PR 或依赖另一功能时按真实目标选择。需要最新远端事实时先通过获授权的读取能力刷新，不能把陈旧本地引用称为最新。用原生 `git -C <仓库> worktree add <项目根内路径> -b <功能分支> <基线SHA>`；分支已被使用时复用原树或选新分支，不强制绕过。创建不复制未提交文件、依赖或凭据；若依赖已有未提交成果，先核对归属，无法判断再提问。不要手改 `.git`、gitdir、commondir 或反向指针。

后续命令显式指定实际 `workdir` 或 `git -C`，文件工具指向该树。一次 shell 的 `cd` 不改变以后工具的目录。将每仓实际路径、基线和分支写入已有工作记录，恢复时重新核验；不通过改任务编号隐式换目录。worktree 只隔离文件和 index，端口、数据库、Docker 服务、缓存及输出需按实际运行配置隔离。后台服务必须由平台管理，不能脱离工具生命周期继续写源码。

安装浏览器或运行构建前，检查实际内存、磁盘空间及已有工具。`/tmp` 是有容量限制的内存盘，下载包、解压文件也占用 Agent 的容器内存；不要将浏览器缓存放到 `/tmp`。优先复用已验证版本的浏览器，否则在当前授权的磁盘可写目录内建立独立缓存与临时目录，通过 `PLAYWRIGHT_BROWSERS_PATH`、`TMPDIR` 指向它们；只读检查使用平台提供的测试产物目录，不改源码、模型会话目录或其他人的缓存。仅需 headless Chromium 时可用 Playwright 的 `install --only-shell chromium`，但系统依赖安装须符合现有权限；无安装权限时报告缺失，不假称浏览器验证通过。缓存不加入提交。命令失败保留真实退出码，不能用管道末尾成功或 `echo` 掩盖安装、构建、测试失败；空间不足先清理自己本轮不再使用的临时文件，再调整目录重试。

修改前读取实际文件，内容冲突重新读取。共享 checkout 只有一个当前分支与暂存区；核对自己的改动块、整个 index 和 HEAD，不默认 `git add .` 包含未知成果，不 reset/clean/stash 他人修改。作者通过本次 Git 操作参数设置，不反复改共享 `user.name/email`。只运行相关验证；在选定树提交，按已有授权通过 `fde_git_push`、`fde_pr_create` 指定 repository_id、checkout_relative_path 和精确 commit_sha，功能分支直接送审，不先合本地默认分支。具体操作待审批时保存其 request_id 并等待，未回答不是批准；结果未知先查询实际状态，不盲重放。

有关联任务且本次要求交付送审时，以当前任务、实际 checkout 和最终提交衔接验证与 PR：准备阶段用 `fde_task_complete(submit=false)` 运行检查只算验证；需要 PR 时，推送已验证提交，调用 `fde_pr_create` 用 `work_item_ids` 明确本次交付涉及的任务，核对返回的仓库、PR 和精确 head。审批恢复后核对原请求的工具、完整参数和当前绑定；未变化则继续原批准操作，正文也不重新改写。版本、HEAD 或绑定漂移时先停止旧恢复、查询实际状态，需要修改操作则重新检查并申请当前精确参数的批准，不换参套用旧许可。最终查询任务当前版本，使用实际 `checkouts`、相关 `checks` 和 `expected_version` 调用 `fde_task_complete(submit=true)` 送审；跨轮恢复或提交变化时在当前执行中重新检查，不以旧 proof 代替。响应 `status=passed` 只说明检查通过，还要核对 `submission_state=submitted`、任务进入 `in_review` 及所需 PR 的交付关联，再回报已送审。`verify_only` 表示未送审；`not_submitted` 或缺少字段时按返回原因、任务和交付查询处理，无法确认就报告未确认，不写成已交付。用户只要求设计、阶段验证或保留本地成果时按对应范围结束，不因此推送、开 PR 或送审。

跨仓交付分别保存 commit/PR、接口依赖和合并顺序，验证记录列出全部参与组件的精确 SHA；有未提交改动时另记内容摘要和配置。只有一仓交付时报告部分完成，PR 合并和业务验收另据事实更新任务；普通回复结束不自动等于任务完成。送审不授予合并权限，也不把任务直接变成 `done/closed`，最终验收由有权限的人完成。

只有用户范围包含清理且成果已保存、不再使用时才移除 worktree。先检查使用者/进程、dirty/staged、未跟踪及需保留的忽略文件，以及未推送/游离提交是否有保留引用；再用普通 `git worktree remove`。拿不准则保留，不强制清理未知目录，不以任务或容器结束触发删除。
